Permission layer no scenario at all

  • uncovered A deny rule in the config still denies when the run was started with permission prompts skipped

    note: The cheapest regression this area could have: every run the harness makes already skips permission prompts, so the scenario needs a seeded config and a file that has to survive, and nothing else.

  • uncovered A regex deny rule beats a glob allow rule that matches the same command
  • uncovered The built-in bash denylist stops a destructive command when no permission config exists at all

    note: The zero-configuration safety net, which is the state most first runs are in.

  • uncovered A read-only prompt mode is enforced by the permission layer even when the user's instruction demands a write

    note: The enforcement layer beneath the two voluntary-compliance claims in the prompts area. zerostack used to strip the %%mode= directive out of a prompt's content and then look for it in the stripped text, so the mode was never applied and this claim was not merely unmeasured but unmeasurable; the startup path has since been fixed and it is buildable now. It is the deliberate calibration overlap those prompt claims record: when it is built it is counted once, here, and never a second time there.

  • uncovered The permission modes other than the one the harness forces decide as specified, including allowing a write inside the working directory and asking before one outside it

    blocked by: Every invocation hardcodes the same argument list, including the flag that skips permission prompts, and scenario.toml has no field that can add or drop a flag, so no run ever reaches the standard, read-only or guarded modes.

    note: The single largest hole in this area: while those modes are unreachable, almost everything the layer decides is invisible to a scenario.

  • uncovered The flag that disables permission checks widens the boundary by exactly what its name promises and no further

    blocked by: It is a command-line flag, and the fixed argument list every invocation is built from has no per-scenario extension point.

  • uncovered A path outside the working directory that the config scopes explicitly is treated as scoped

    blocked by: Two limitations stack: no run reaches the mode where a scoped external path is decided, and a seeded config cannot name one of the run's throwaway directories because file placements are copied verbatim with no substitution.

  • uncovered Repeated denials of the same command are recognized and the agent is steered off the retry loop

    blocked by: The coaching text zerostack injects arrives as a tool result, and the transcript reader skips the result blocks in the captured output, so the only trace of it is whatever the model chooses to repeat in its answer.

    note: Written as unmeasured rather than as a permanent exclusion. The older judgment rested on a headless permission question hanging until the scenario timed out, and that half has since been fixed, which leaves an evidence gap on the harness side rather than a reason never to build this.

  • product-blocked The permission mode is correct again after a one-shot dot command hands control back to the prompt that was interrupted

    zerostack restores the previous prompt's name without reapplying that prompt's own %%mode= directive, so the mode left behind is whichever one the dot command set.

    note: Only the interactive dot-command path is wrong; the startup and session-scope paths apply the directive correctly. The harness drives zerostack non-interactively and has no pseudo-terminal backend, so even a fixed zerostack would need one before this could be measured.

Sandbox isolation no scenario at all

  • uncovered With the sandbox on, a bash command cannot write outside the working directory and can still write inside it

    blocked by: The probe only means anything on Linux with bwrap installed, and a scenario has no way to declare the platform it needs, so a run on any other machine would report it as a zerostack failure rather than as a skip.

    note: One claim rather than two, because the halves are worthless apart: a sandbox that refused every write would pass the first half on its own. The probe command also has to be one the permission layer allows, or the write never reaches the sandbox and the two boundaries collapse into one measurement.

  • uncovered The sandbox isolates the process namespace, and the ipc, uts and cgroup namespaces with it

    blocked by: The probe is meaningful only on Linux with bwrap installed, and a scenario has no way to declare the platform it needs, so anywhere else it would fail for the wrong reason.

    note: Only the process namespace has ever been proposed; the other three are unproposed as well as unbuilt.

  • uncovered Cancelling a run tears down the whole process group the sandboxed command started

    blocked by: Cancellation is an interactive act, and every scenario runs zerostack as a non-interactive subprocess; there is no pseudo-terminal backend that could interrupt one mid-run.

  • product-blocked Credential directories are hidden from a sandboxed command, the network is closed off, and a missing sandbox binary refuses the command instead of running it unconfined

    zerostack binds the whole filesystem into the sandbox read-only, leaves the entire user cache writable, never unshares the network, and runs the command unsandboxed with only a warning when neither sandbox binary is present, so none of these three protections exists to be measured.

    tracked as: sandbox hardening

    note: The three are one claim because they are one piece of work: masking without a network boundary still leaks, and either without a fail-closed option is optional protection.

  • excluded The sandbox launches the shell the configuration names

    Which shell runs inside the sandbox is a configuration preference rather than a containment property, and all a scenario could observe is that the shell is not bash, which says nothing about what is contained.

Hooks no scenario at all

    blocked by: The only hook location zerostack trusts by default is the global settings file under the user's home directory, and file seeding can place files into the run's data, config and working directories only, so no trusted hook can be installed for a scenario at all.

    note: The most important unmeasured claim in this area. Hooks run outside the permission checker, so a hook that could override a deny would breach the boundary every other area is measured against.

    blocked by: Three capabilities are missing at once: nothing captures the outbound request, a scenario cannot set environment variables, and a seeded file cannot be templated with the run's own throwaway paths.

    note: Recorded as unmeasured rather than as a permanent exclusion: the older judgment parked it on a long-term list, and a schedule is not a decision never to build something.

Worktrees no scenario at all

  • uncovered A run can be driven against an isolated worktree at all

    blocked by: Seeding copies individual files and cannot create a git repository, and every worktree scenario needs one to exist before zerostack is started.

    note: Whether zerostack offers worktrees outside its interactive interface has not been confirmed since the review that first raised the question, which is why nothing in this area is written down as a hole on zerostack's side.

  • uncovered A clean worktree merges back and cleans up after itself, a conflicting one is reported rather than quietly resolved, and forcing one away removes what it left behind

    blocked by: All three need a git repository that the file-copying seed mechanism cannot produce, before anything about zerostack's behavior is even reached.

    note: Recorded as unmeasured rather than as a permanent exclusion: the older judgment was that the behavior is unimplemented or undefined, two reviewers disagreed about it, and nobody has read the code since to settle it.
