# Decisions: coverage-ledger

Post-start rulings for this change, each dated, tagged, and sourced.
`design.md`'s Non-Goals and D1-D13 are the pre-start record and are never
edited here; this file holds what was decided after implementation began.

Created 2026-07-29 by the preflight gate, which is the first run that produced
rulings for this change. Nothing before that date was reconstructed.

Extended 2026-07-30 after a `/vibe-diff` review of the same branch, which the
author answered with "fix them all". Two of 07-29's `[tracked]` deferrals are
reversed by that ruling; they are recorded as reversals below rather than edited
away, so the reasoning that deferred them stays readable.

Extended again 2026-07-30 by `/ship`'s adversarial review gate, a fresh-context
pass reading the diff as an outside contributor who saw none of the above. It
found eight, seven of them in rules the earlier rounds had already touched and
believed closed, which is the argument for running the gate on a branch that has
already been reviewed twice.

- 07-29 [included] `audited_against` and `scenario_roots` are now rejected when empty, a load-time rule the spec's list did not carry: `audit_matches` is containment, and `"".contains()` matches every banner, so an empty value would report the ledger as audited against a mock report instead of mismatching it. That is a wrong version claim, the one outcome D6 says must never happen (source: preflight step 3, defect axis)

- 07-29 [caveat] The three `product-blocked` claims citing `issue #227` and `issue #229` are true against `audited_against = "1.7.2"`, but ROADMAP_ZS.md's 07-27 update records both as implemented upstream and filed as PR #228 / #230, with the zseval-side work explicitly waiting on those merging into the fork. The claims are correct as written and stay; they need re-adjudication at the next audit, when `audited_against` moves past 1.7.2 (source: preflight step 5, main session)

- 07-29 [caveat] `zs` carries three citation shapes: a GitHub issue (`issue #227`), an upstream roadmap work item (`sandbox hardening`), and a source marker (`TODO(loop-history)`). All five values resolve to real tracking entries; upstream tracks these things in three different places, and D2 prefers a string that names its subject over an index a re-plan can move. Not normalised on purpose (source: preflight step 3, standards and spec axes)

- 07-29 [caveat] The file-order half of the spec's "the ledger declares all 15 areas" scenario is pinned only on the inline fixture; the integration test sorts before asserting. Deliberate: spec.md line 10 and D11 make file order presentation order, so re-sequencing the page must stay free. Only the set is pinned (source: preflight step 3, spec axis)

- 07-29 [reversal→denied] The standards axis asks that `scenarios/coverage.toml` gain an entry in README's Layout block (README.md:23-37). This contradicts proposal.md's "No new CLI subcommand and no README section" and D8. The same reviewer noted `scenarios/PLAN.md` is absent from that block too, so no established rule is breached either way. Put to the author, who ruled the same day: keep the Non-Goal, no README entry (source: preflight step 3, standards axis)

- 07-29 [tracked] `scenario::discover`'s three silent skips (an unreadable directory, a failed `DirEntry`, and no descent into a directory that already holds `scenario.toml`) mean the "every scenario is claimed" direction can under-enumerate the tree and still report clean. Pre-existing `discover` behaviour that this change newly makes load-bearing for a correctness guarantee; no nested scenario exists today. Registered in ROADMAP.md rather than fixed here, because the fix touches `scenario.rs`, which proposal.md's Impact section puts out of scope (source: preflight step 3, defect axis)

- 07-29 [tracked] `check_ids` tests membership, not multiplicity, so two scenarios sharing one id, or overlapping `scenario_roots`, are both satisfied by a single covered claim and the check passes. Nothing in the repo rejects duplicate scenario ids today. Registered in ROADMAP.md together with the `discover` uniqueness check it wants (source: preflight step 3, defect axis)

- 07-29 [tracked] The schema accepts duplicate area names and an explicit `claims = []`, each of which loads clean while making an area account for nothing. The pinned-area-set test catches the duplicate for the real file only. Registered in ROADMAP.md (source: preflight step 3, defect axis)

- 07-29 [tracked] `Ledger`'s fields are `pub` and `check_unique_ids` runs only inside `parse`, so a hand-constructed `Ledger` (the likely shape of a Day-2 renderer fixture) can carry a duplicate id unchecked. D5's invariant is load-path-only. Registered in ROADMAP.md against Day 2 (source: preflight step 3, spec axis)

- 07-30 [included] `audit_matches` refuses a hit glued to a character that could extend a version: a digit or `.` on either side, and `-` or `+` after it. Plain `str::contains` failed in the exact direction D6 promises is impossible, since `1.7.2` is a substring of `zerostack 1.7.20` and of `zerostack 1.7.2-rc1` — a *newer* binary read as a match, and the page would have made a wrong version claim rather than the spurious mismatch the design is willing to pay for. Still not a parse: nothing splits on dots, orders two versions, or assumes where in the banner the version sits, and anything the rule gets wrong still fails as a mismatch. spec.md gained the rule and three scenarios (source: /vibe-diff review 07-30, hotspot 1)

- 07-30 [reversal→included] The 07-29 `[tracked]` ruling on `check_ids` testing membership rather than multiplicity is reversed. The check now reports an id declared by more than one scenario under `scenario_roots` as a third drift category, named once per id rather than once per copy. The deferral rested on the fix wanting a uniqueness check inside `scenario.rs`, which proposal.md's Impact section puts out of scope; refusing the duplicate inside `coverage.rs` needs no such change and closes the ledger's own guarantee, which is where the spec makes the promise. `discover` still neither dedupes nor rejects, so the ROADMAP.md entry stands for the scenario-loader half (source: author ruling 07-30, on /vibe-diff review hotspot 2)

- 07-30 [included] `reject_foreign_evidence` derives each status's foreign set as the complement of the fields that status owns, against one shared presence list, replacing four hand-maintained complement tables with nothing deriving one from another. The eleven-pair test stays: the derivation moves the ways to be wrong rather than removing them, to an `owned` list naming a field the status should not accept, or a field added to `RawClaim` and left out of the presence list, which would then be accepted under all four statuses at once (source: /vibe-diff review 07-30, hotspot 3)

- 07-30 [included] The malformed-ledger test now also drives a mock-backend `zseval run`, the command spec.md's scenario and tasks.md 5.1 both name; it previously pinned `zseval list` alone. Mock replays a canned session, so covering the real command costs no API key and the trial's verdict is deterministic enough to assert outright. The stronger guarantee remains structural rather than asserted: `coverage::` and `Ledger` appear nowhere outside `tests/harness.rs` (source: /vibe-diff review 07-30, hotspot 5)

- 07-30 [denied] The review's remaining focus, the seven `excluded` entries, takes no code fix and was not given one: an exclusion has no failing state by construction, which is exactly why D13 made re-adjudication an authoring rule and section 5.3 handed the block to the author instead of to a test. Re-confirmed on 07-30 that the two entries D13 named as known-expired are present as `uncovered` with a note recording the demotion. The seven that remain rest on ROADMAP_ZS.md's 07-26 reading and fall due at the next audit, when `audited_against` moves (source: author ruling 07-30)

- 07-30 [reversal→included] The 07-29 `[tracked]` ruling on `scenario::discover`'s three silent skips is reversed, and with it proposal.md's "no changes to `scenario.rs`". An unreadable directory and a failed `DirEntry` now propagate with context instead of being skipped, and a `scenario.toml` nested under another scenario is refused by name rather than passed over. The deferral was right while `discover`'s result only fed a run, where a suite short a case is visible; it stopped being right once `check_drift` made the same function the authority on which scenarios exist, because a silent skip there reports full coverage of a tree the check never saw. Nesting is refused rather than supported: a scenario directory is a leaf, so a scenario under one has no sensible reading, and the single-scenario shorthand stays exempt because a caller naming one directory is not asking for a survey. No nested scenario exists today and no in-tree directory is unreadable, so the real suite is unaffected: 354 tests green (source: author ruling 07-30, on /vibe-diff review risk 4)

- 07-30 [reversal→included] The 07-29 `[tracked]` ruling on duplicate area names and an explicit `claims = []` is reversed: both are load errors now, reported together and by name. An area is one row of the denominator, and the pinned area-set test cannot see either fault, since sorting the names of a file with a doubled area still yields every name the spec expects (source: author ruling 07-30)

- 07-30 [reversal→included] The 07-29 `[tracked]` ruling that D5's invariant is load-path-only is reversed rather than deferred to Day 2. `Ledger`'s three fields are private, `Ledger::new` is the only constructor and runs the header, area and duplicate-id checks, and reading is through `audited_against()`, `scenario_roots()` and `areas()`. The deferral treated this as Day-2 API shape, but the cost of settling it later is a renderer whose first hand-built fixture is already outside every rule this module enforces, and settling it now costs three accessors and one call site in `tests/harness.rs`. Pre-launch, so no compatibility concern (source: author ruling 07-30)

- 07-30 [denied] `discover`'s new strictness reaches `zseval run` and `zseval list`, not only the drift check, and that is kept. The review is right that the 07-30 reversal argued only the coverage-correctness side, and right that the blast radius is real: both commands take a user-supplied path, so a tree holding one unreadable subdirectory now fails the command instead of running the scenarios it can see. The suggested split, a lenient `discover` plus a strict variant for `check_drift`, was declined. A run whose suite is silently short a case produces a report whose aggregate numbers are wrong and says nothing about it, which is the same failure the reversal was paid to close, one consumer along. Loud is the right answer on both paths, and no in-tree directory is unreadable, so nothing in this repo changes. Recorded here because nowhere else weighed the run path (source: /ship adversarial review 07-30, finding 1)

- 07-30 [included] The walk now skips a `_fixtures` subtree outright. Pushing a scenario directory back onto the stack, which is what makes a nested scenario findable, walked its fixtures for the first time; fixtures are seed data, so a file called `scenario.toml` there is a payload, the file a "fix the syntax error in this config" task hands the agent. One such fixture would have bailed the walk and taken down every `list`, every `run` and the drift test over the whole tree, naming the author's fixture a nested scenario. Fifteen `_fixtures` directories exist today and none holds one, so this was a trap rather than a failure. Closing it also withdraws the walk from fixture trees, which returns `discover`'s symlink exposure (`is_dir` follows links, nothing bounds depth) to exactly what `main` has; that remains pre-existing and out of scope (source: /ship adversarial review 07-30, finding 2)

- 07-30 [included] Each entry of `scenario_roots` is now checked at construction: absolute entries, `..` components, and entries naming no directory below the repo root are load errors. The entries are the sole input to a filesystem walk and are joined onto the repo root, and joining onto a path discards it when the operand is absolute, so an unchecked entry did not fail, it walked somewhere else on the machine; `""` and `"."` resolved to the checkout and sent the walk into `target/` and `.git`. `check_header` had rejected only an empty array. A bare `.` component is allowed, since it changes nothing and `./scenarios` is a legitimate spelling; what is refused is an entry with no `Normal` component at all (source: /ship adversarial review 07-30, finding 3)

- 07-30 [included] The required-evidence rules move off the load path onto the type, completing the 07-30 ruling that made `Ledger`'s fields private. `Ledger::new` ran the header, area and duplicate-id rules only, while the module header and spec.md both claimed every rule held for any way of constructing a ledger value; `Area` and `Claim` carry public fields and so do `Status`'s variants, so a covered claim citing nothing, a blank `reason` and a claim with no text were all constructible and all passed. Moved rather than duplicated: `RawClaim::validate` keeps only what the flat wire shape alone can ask, and `check_claims` holds the rest. Blank now counts as absent throughout, which also closed `reason = ""` on the load path. `Area::title` stays unchecked: it is presentation text whose emptiness shows up on the rendered page (source: /ship adversarial review 07-30, finding 4)

- 07-30 [reversal→included] The overlapping-roots half of the 07-29 `[tracked]` ruling on `check_ids` is reversed and closed; the duplicate-id half was already closed on 07-30. Overlapping roots enumerated every scenario below the inner one twice, and the duplicate-id rule reported that as two scenarios sharing an id: a true statement about the walk and a false one about the tree, naming healthy scenarios for a defect in one line of the header. Caught in two places because it is two facts. `check_roots` compares the entries as written, which normalises spelling so `scenarios` and `./scenarios` are one tree and belongs where every other ledger rule lives; `check_drift` compares canonicalized paths, the only way to see a symlinked root, and needs a repo root that construction does not have (source: /ship adversarial review 07-30, finding 5)

- 07-30 [included] A scenario id listed twice inside one claim's own `scenarios` array is now reported as that, rather than as the same claim colliding with itself. `check_unique_ids` collected one reference per occurrence and rendered every one, so the error read `'x' is claimed by 'c' (area a) and 'c' (area a)` and sent the author looking for a second claim that does not exist. The rejection was right; only the message moved (source: /ship adversarial review 07-30, finding 6)

- 07-30 [included] `audited_against` is trimmed in `Ledger::new`. `check_header` tested `trim().is_empty()` while the field kept the file's value verbatim, so `" 1.7.2 "` loaded clean and `audit_matches` then searched a banner for the literal spaces, applying the character-boundary rule to them instead of to the digits. The result was a permanent version mismatch against every binary with nothing to explain it, which is the same silent-wrong-answer family as the empty value closed on 07-29 (source: /ship adversarial review 07-30, finding 7)

- 07-30 [denied] `reason` and `blocked_by` are specified as one-line and stay unenforced beyond non-blank. The review is right that the module rejects far smaller things and that no artifact said why this one is exempt, which is the part worth recording: a length or newline limit on prose is a formatting rule, not a truth condition, and the renderer that lays these out beside their claim is Day 2's problem to solve with layout rather than the loader's to solve with a refusal. What the loader owes is that the field says something, which `check_claims` now enforces (source: /ship adversarial review 07-30, finding 8)
