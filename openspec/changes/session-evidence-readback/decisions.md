- 08-02 [included] Task 9.2's first live run found `session-tool-call-recorded` asserting `tool_called read`, which turned out to be a claim about which tool the model picks rather than about the evidence channel: the model answered "What is the launch code recorded in notes.txt?" with `bash cat notes.txt` instead of the `read` tool, so the scenario read as a random failure rather than a regression pin. The fix is a new name-agnostic assert, `tool_called_any` (section 10), not swapping the pinned name to `bash`: hardcoding whichever tool the model happened to pick on that run would only relocate the same defect to a different name. The live `tool` records themselves matched design D1's mirror field for field on both the `tool_call` and `tool_result` roles (`{"id":0,"name":"bash","args":{...}}` / `{"call_id":0,"name":"bash","truncated":false,"full_output_path":null}`), so the regenerated fixtures from section 1 stand unchanged (source: 9.2 first run, 2026-08-02)
- 08-02 [reversal→accepted] Preflight's defect review asks that `session-prompt-recorded-stock` stop hardcoding `built_in`, because `ZsCli::run` seeds a `--prompts` pack into every trial of every scenario (`backend.rs:406-413`) and README's own prompts section says a pack shipping `code.md` reaches scenarios that declare no prompt: so `zseval run scenarios --prompts <pack with code.md>` makes that session record `code`/`user_file` and the pin fails 3/3 on a supported, documented configuration with nothing wrong in the product. This contradicts a recorded decision twice over: design D6 specifies the pin as `prompt_recorded code built_in` "on a bare run", and the `session-evidence` delta spec's "Regression scenarios pin both channels" requirement states the same in requirement text. Naming `built_in` is also the pin's whole point (it proves the compiled-in default is recorded as such), so the fix is not the same move section 10 made for the tool pin. Put to the user, who accepted the reversal and asked for it to be fixed in this change; D6's "bare run" wording and the delta spec's requirement text both move with it (source: preflight step 3 defect review, 2026-08-02)
- 08-02 [tracked] `scenario_seeds_prompt` (`runner.rs:147`) recognises only a `work:.zerostack/prompts/<name>.md` seed, but `seed.rs` also supports a `data:` root and `$ZS_DATA_DIR/prompts` is zerostack's global prompt layer (`../zerostack/src/context/prompts.rs:8`, `global_dir`). A scenario seeding `dest = "data:prompts/<name>.md"` would therefore read back `user_file`, match neither branch of D3's mapping, record `unknown`, and warn that "the trial environment is not what the harness planted" about a file the harness itself planted. No committed scenario does this today, so it is a latent misdiagnosis rather than a defect in this change. Registered in `ROADMAP.md` under "已登記 finding(2026-08-02 session-evidence-readback preflight,未修)", the destination the user confirmed (source: preflight step 3 defect review, 2026-08-02)
- 08-02 [included] Fixing the trial-failure misdiagnosis (task 11.2) added a distinction design D4 did not draw: a trial can now report an *observed* absence (its session parsed and carried no `prompt` field, which is the PR #228 case) separately from having observed nothing at all (no readable session, from a backend error or a schema `Err`). `GradedTrial.prompt` became a three-variant `PromptReadback` and `reconcile` filters the unobserved trials out before reconciling, so a failed trial can no longer masquerade as evidence about the binary's age or as disagreement. D4's two named failure cases and their messages are unchanged; this only stops a third state from borrowing them (source: preflight step 3 defect review, 2026-08-02)
- 08-02 [tracked] Implementing 11.3 surfaced a pre-existing cosmetic edge: the run summary's total cost is an `f64` sum, so an empty trial set yields `-0.0` and prints `$-0.0000`. It already existed (every report's empty `capability` block carries `pass_at_k: -0.0`); 11.3 only makes it reachable on the overall line, in the degenerate run whose every scenario was skipped for pack shadowing. Value equals zero, so nothing downstream is wrong. Registered on `ROADMAP.md` beside the other unfixed findings rather than fixed here (source: preflight step 5 triage, 2026-08-02)
- 08-02 [caveat] Preflight's standards review raised one judgement call and no hard findings: `record_prompt` (`runner.rs:287`) runs about 80 lines carrying four mapping arms plus two reconciliation-failure branches. Kept as is. The branches are irreducible (four source layers, two disagreement modes that must carry different messages because they have different fixes), the function is already decomposed into `reconcile`, `describe_readbacks`, and `source_label`, and every branch is documented; the reviewer's own verdict was that it should not block. Splitting it further would scatter one readable mapping across helpers that only ever have one caller (source: preflight step 3 standards review, 2026-08-02)
